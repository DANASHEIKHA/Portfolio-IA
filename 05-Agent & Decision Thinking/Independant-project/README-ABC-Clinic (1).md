# ABC Clinic Appointment Booking AI Agent

وكيل ذكاء اصطناعي على n8n يستقبل طلبات حجز المواعيد عبر Telegram، ويجمع معلومات المريض، ويتحقق من المواعيد المتاحة، ويطلب التأكيد الصريح، ثم يثبّت الحجز في Google Sheets ويتحقق من نتيجته.

> الأجزاء بين `[ ]` تحتاج تعبئتها بنتائجك الفعلية قبل التسليم. جدول الاختبار فيه السيناريوهات والسلوك المتوقع من المتطلبات، أما النتائج فتُكتب من تجاربك فقط.

---

## 🎯 Problem

### The Context
تستقبل عيادة ABC Clinic طلبات حجز مواعيد من المرضى، وتحتاج إلى جمع معلومات محددة (الاسم، الهاتف، حالة المريض، نوع الزيارة، التاريخ والوقت) والتأكد من توفر الموعد.

### The Problem
[اكتبي بكلماتك المشكلة الحالية في الحجز اليدوي، مثل: ضغط على الاستقبال، تكرار الأسئلة، أخطاء في تثبيت المواعيد]

### Why It Matters
الحجز غير المؤكد أو المكرر أو المعلن نجاحه دون حدوثه يضر بالمرضى وبالعيادة. كما أن الحالات الطبية والطارئة يجب ألا تُعامل كطلبات حجز عادية.

---

## 💡 Solution
Agent في n8n يقترح الإجراء التالي بصيغة منظمة (Structured Output)، بينما عقد الـ Workflow هي التي تفحص الشروط وتنفذ الحجز. الـ Agent **لا يملك أداة كتابة** على الجدول، فلا يعتمد منع الحجز غير المؤكد على التزام النموذج بالتعليمات وحدها.

### What does the system do?
- يرحّب بالمريض ويسأل عن نوع الزيارة وموعدها.
- يقبل المعلومات بأي ترتيب ويسأل عن الناقص فقط، سؤالًا واحدًا في كل مرة.
- يقرأ المواعيد المتاحة عبر أداة قراءة فقط قبل اقتراح أي موعد.
- يعرض ملخصًا من ست قيم ويطلب تأكيدًا صريحًا.
- بعد التأكيد، يمر الطلب عبر Gate في الـ Workflow ثم يُحدَّث الصف ويُقرأ من جديد للتحقق.
- يصعّد أو يتوقف في حالات: الطارئ، السؤال الطبي، الإلغاء والتعديل، الحجز لعدة أشخاص، الشكاوى.

## 👤 Users

**Primary Users:**
مرضى عيادة ABC Clinic عبر Telegram، وموظفة الاستقبال التي تستلم التنبيهات.

**User Need:**
المريض يريد حجز موعد بسهولة، والموظفة تريد حجوزات صحيحة ومؤكدة وتنبيهات للحالات التي تحتاج تدخلها.

## 🧠 How I Designed the Solution
- **مبدأ التصميم:** يجمع، يتحقق، يؤكد، ثم ينفذ، ويعرف متى يسأل أو يصعّد أو يتوقف.
- **فصل القرار عن التنفيذ:** الـ Agent يقترح `action` فقط، والتنفيذ في عقد الـ Workflow.
- **حالة المحادثة في ورقة Sessions** (state وpending_key) وليس في الذاكرة، لأن Simple Memory ليست مصدرًا موثوقًا لحالة الحجز.
- **pending_key:** بصمة للملخص المعروض، فلا يُقبل التأكيد إلا على بيانات مطابقة تمامًا لآخر ملخص.
- **حماية من الأحداث المكررة** بمقارنة `update_id` مع `last_update_id`.
- [أضيفي أي قرار تصميم آخر اتخذتِه فعلًا]

## ⚙️ How It Works

```
Telegram Trigger
      |
Get Session  ──>  Duplicate Event Check
      |
   AI Agent  (Chat Model + Memory + check_availability + Structured Output Parser)
      |
Validate Output (Code)
      |
Switch (action)
  |-- ask_info / refuse / escalate / emergency  ──> Upsert Session ──> Telegram Reply
  |-- show_summary ──> Upsert Session (AWAITING_CONFIRMATION + pending_key) ──> Telegram Reply
  |-- confirm_booking ──> Gate ──> Re-read Slot ──> Update Row ──> Read Back ──> Verify ──> Reply
```

## 🤖 Role of AI

**What does AI do in this solution?**
- يفهم رسائل المريض (عربي أو إنجليزي) ويستخرج الحقول الستة.
- يحل التواريخ النسبية (مثل "الأحد القادم") اعتمادًا على تاريخ اليوم.
- يقرر الإجراء: ask_info أو show_summary أو confirm_booking أو escalate أو refuse أو emergency.
- يقرأ المواعيد المتاحة ويقترح أقرب موعدين عند عدم توفر الموعد المطلوب.

**What AI Should NOT Do**
- لا يعطي نصائح طبية أو تشخيصات أو معلومات أدوية، ولا يسأل عن الأعراض.
- لا يذكر أسعارًا أو تأمينًا أو سياسات لم تُعطَ له (يصعّد للموظفة).
- لا يلغي أو يعدّل مواعيد ولا يحجز لعدة أشخاص.
- لا يقول إن الحجز تم؛ النظام وحده يؤكد ذلك.
- لا يخمّن أو يخترع قيمة، ولا يتجاوز قواعده بطلب من المريض.
- لا يملك أي أداة كتابة على الجدول.

## 🔄 Automation
- استقبال الرسائل عبر Telegram Trigger.
- قراءة حالة الجلسة وفحص الرسالة المكررة.
- التحقق من مخرجات الـ Agent بعقدة Code (الإجراء، الصيغ، قاعدة Follow-up، حالة التأكيد، تطابق pending_key).
- توجيه الإجراءات عبر Switch وتحديث ورقة Sessions.
- مسار الحجز: قراءة الصف مجددًا، التحقق من أنه Available، تحديثه، قراءته بعد التحديث، والتحقق من القيم.
- تنبيه الموظفة عبر Telegram عند التصعيد أو الطوارئ أو فشل التحقق.

## 🗂️ Data

**Input**
رسائل نصية من المريض عبر Telegram، بالإضافة إلى حالة الجلسة وتاريخ اليوم.

**Output**
- ردود الـ Agent على Telegram.
- تحديث صف الموعد في ورقة `Schedule`.
- حالة المحادثة في ورقة `Sessions`.

**ملف Google Sheets:** `ABC Clinic Appointments`

| الورقة | الأعمدة |
|---|---|
| Schedule | Date, Time, Status, Patient Name, Phone Number, Patient Status, Visit Type |
| Sessions | chat_id, state, pending_key, last_update_id, updated_at |

**الحقول التي يجمعها الـ Agent:** patient_name، phone_number، patient_status (New/Existing)، visit_type (General Checkup / Follow-up / Vaccination)، appointment_date (YYYY-MM-DD)، appointment_time (HH:MM).

## 🔑 Key Design Decisions

### Decision 1
**Decision:**
عدم إعطاء الـ Agent أي أداة كتابة، وتنفيذ الحجز في عقد Workflow.

**Why:**
لأن System Prompt تعليمات يمكن أن يتجاوزها النموذج أو يتلاعب بها المستخدم؛ الحدود الحرجة يجب أن يفرضها التصميم.

### Decision 2
**Decision:**
حفظ حالة الحجز و`pending_key` في ورقة Sessions.

**Why:**
Simple Memory ليست قاعدة بيانات دائمة ولا مصدرًا موثوقًا لحالة الحجز.

### Decision 3
**Decision:**
إعادة قراءة الصف قبل الحجز وبعده.

**Why:**
لمنع حجز موعد أُخذ في الأثناء، ولعدم الاكتفاء بنجاح عقدة Update Row كدليل على حدوث الحفظ.

### Decision 4
**Decision:**
الإيقاف والتصعيد في حالات الطارئ والطب والإلغاء والمجموعات.

**Why:**
هذه حالات خارج صلاحية وكيل الحجز، وبعضها يتعلق بسلامة المريض.

## 📚 What I Learned

**Technical Lesson**
[ما تعلمتِه عن الجلسات والذاكرة وSwitch وGate في n8n]

**Problem-Solving Lesson**
لا يكفي أن يقول الـ Agent إنه لم يحجز؛ يجب فحص سجل Executions وورقة Schedule.

**AI Lesson**
الحدود الحرجة تُفرض بتصميم الـ Workflow، وليس بالأمل في التزام النموذج بالتعليمات.
